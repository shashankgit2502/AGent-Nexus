# Decentralized Peer-to-Peer Multi-Agent System — Architecture & PRD

**Version:** 1.0 (blueprint, pre-implementation)
**Stack:** Python · FastAPI · LangChain v1 · LangGraph v1 · PostgreSQL · React
**Document purpose:** Single source of truth for the system design. Every load-bearing decision is locked. Code snippets are illustrative of the *real* APIs to use (LangChain v1 / LangGraph v1); this document precedes the runnable scaffold.

---

## 1. One-line summary

A decentralized, hackathon-style multi-agent platform where a user creates a **Team**, configures **peer ReAct agents** (each with its own persona, tools, skills, memory, and LLM), and launches a collaboration session in which agents reason together over a **shared blackboard** — no master, no fixed A→B→C flow — converging on a single output through confidence-weighted consensus, gated by a human before final synthesis.

---

## 2. Core principles

1. **No master agent, no hierarchy.** The Orchestrator is an *entry node* (prompt-engineer + spawner) and goes passive after dispatch. It is not a runtime controller.
2. **Mesh, not pipeline.** Within a round, every agent reads every peer's latest contribution. There is no predefined agent-to-agent edge set.
3. **Emergence through iteration.** The solution is co-evolved over debate rounds, not merged once at the end.
4. **Real frameworks only (NFR).** Agents are built with `langchain.agents.create_agent`; state, persistence, and control flow use LangGraph primitives. **No custom state machine, checkpointer, agent framework, or graph runtime is to be reimplemented** where LangGraph/LangChain already provides one.
5. **Runtime configurability.** Agents are spawned at runtime; LLMs, tools, and skills are selected per agent at runtime; new providers/models are added through Settings without code changes.

### 2.1 The DAG-vs-mesh reconciliation (read this first)

The system is often described as both "a DAG" and "no fixed flow." Both are true because they describe **two different levels**:

- **Outer level — the DAG (with a loop).** A LangGraph `StateGraph` defines the control skeleton:
  `Orchestrator → Mesh Round ↺ Consensus Check → HITL Gate → Synthesizer → End`.
  The "DAG" is this skeleton; the loop is the debate rounds.
- **Inner level — the mesh (no fixed flow).** Each Mesh Round uses `Send()` to fan out to **all active agents in parallel**. Every agent reads the *entire* blackboard and writes back independently. There is no ordering between agents and no master. That is the hackathon mesh.

```
                              ┌─────────────────────────────────────────┐
   OUTER GRAPH (control DAG)  │                                         │
                              ▼                                         │
   User Query ──► Orchestrator ──► Mesh Round ──► Consensus Check ──────┘ (loop if not converged)
                  (entry node)        │                  │
                                      │                  ▼ (converged)
                                      │            HITL Gate ──► Synthesizer ──► End Node
                                      │
            INNER MESH (per round) ───┴───────────────────────────────────────────
            Send() fan-out, fully parallel, every agent reads the whole blackboard:

                                       Agent 1
                                   ↗      ↕      ↖
                          Agent 5 ◄──► Agent 2 ◄──► Agent 3
                                   ↖      ↕      ↙
                                       Agent 4
                          (all read/write the shared Blackboard; no fixed edges)
```

## 4. Component architecture

### 4.1 Orchestrator (entry node)
- Receives the user query + team goal.
- Acts as **prompt engineer**: turns the raw query + each agent's persona into per-agent task framing.
- Acts as **spawner**: instantiates the ReAct agents for the round (runtime spawning).
- Writes the initial goal + task framing to the blackboard, then becomes passive.
- Uses a cheap `small_model` (prompt engineering is lightweight).

### 4.2 Agent mesh (peer ReAct agents)
- Each agent = `create_agent(...)` (ReAct loop + middleware).
- Per round, fanned out with `Send()` and run **in parallel**.
- Each agent: reads the whole blackboard → runs its ReAct loop (may call tools) → writes a contribution + self-reported confidence + optional critiques of peers.
- Agents are **tool-calling models only** (hard gate — see §9.2).

### 4.3 Blackboard (shared state)
- A typed LangGraph state object with append-reducers (§6).
- The "every agent talks to every agent" requirement is realized as "every agent reads/writes one shared structure" — functionally a fully-connected mesh without O(N²) direct messaging.

### 4.4 Consensus Engine
- After each round, computes convergence (§8).
- Decides loop-again vs proceed.
- On proceed, runs a confidence-weighted vote to select/rank contributions.

### 4.5 HITL Gate
- `HumanInTheLoopMiddleware` / `interrupt()` before synthesis.
- Human can approve, edit, or reject the converged result; state persists via the checkpointer so the run resumes on the same `thread_id`.

### 4.6 Final Synthesizer
- A **plain LangGraph node**, not an agent.
- Merges the consensus-selected contributions into one unified output.
- Tool-calling not required → can run on a cheaper model.

### 4.7 End Node
- Persists the final artifact, emits the terminal AG-UI event, closes the session.

## 6. LangGraph state schema (the Blackboard)

State is a `TypedDict` with reducers. Contributions, critiques, and events are **append-only** (additive reducers) so parallel `Send()` writes merge without clobbering.

```python
from typing import Annotated, TypedDict, Literal
from operator import add
from langgraph.graph.message import add_messages

class Contribution(TypedDict):
    agent_id: str
    round: int
    content: str
    confidence: float          # 0.0–1.0, self-reported, calibrated post-hoc
    tool_calls: list[dict]      # for transparency / AG-UI rendering

class Critique(TypedDict):
    from_agent: str
    target_agent: str
    round: int
    content: str
    severity: Literal["minor", "major", "blocking"]

class CollabState(TypedDict):
    # Goal & framing (written by Orchestrator)
    goal: str
    success_criteria: list[str]
    agent_task_framing: dict[str, str]      # agent_id -> tailored prompt

    # Mesh working memory (append-only, parallel-safe)
    contributions: Annotated[list[Contribution], add]
    critiques: Annotated[list[Critique], add]

    # Consensus bookkeeping
    round: int
    max_rounds: int
    confidence_threshold: float             # τ
    converged: bool
    consensus_ranking: list[str]            # contribution ids, best first

    # Lifecycle
    status: Literal["init", "debating", "consensus", "hitl", "synth", "done"]
    active_agent_ids: list[str]             # dynamic per round (runtime spawn)
    final_output: str | None

    # AG-UI event stream (append-only)
    events: Annotated[list[dict], add]
```

> **Note on per-agent local memory.** The blackboard is the *shared* layer. Each agent additionally has a private long-term namespace in the LangGraph **Store** (§10), so "Research Agent remembers its findings across sessions" without polluting the shared blackboard.

## 7. Graph & node definitions

```python
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.postgres import PostgresStore

def build_collab_graph(checkpointer, store):
    g = StateGraph(CollabState)

    g.add_node("orchestrator", orchestrator_node)     # entry: framing + spawn
    g.add_node("agent_turn", agent_turn_node)         # one ReAct agent's round (fanned out)
    g.add_node("consensus", consensus_node)           # convergence + weighted vote
    g.add_node("hitl", hitl_node)                     # interrupt() for human review
    g.add_node("synthesizer", synthesizer_node)       # plain node, merges output
    g.add_node("end_node", end_node)

    g.add_edge(START, "orchestrator")
    g.add_conditional_edges("orchestrator", fan_out_to_mesh)   # -> list[Send("agent_turn", ...)]
    g.add_edge("agent_turn", "consensus")                       # all agent_turns join here
    g.add_conditional_edges("consensus", route_after_consensus) # loop or proceed
    g.add_edge("hitl", "synthesizer")
    g.add_edge("synthesizer", "end_node")
    g.add_edge("end_node", END)

    return g.compile(checkpointer=checkpointer, store=store)

def fan_out_to_mesh(state: CollabState):
    # Dynamic, parallel fan-out to every active agent — the mesh, no fixed edges.
    return [
        Send("agent_turn", {"agent_id": aid, **state})
        for aid in state["active_agent_ids"]
    ]

def route_after_consensus(state: CollabState):
    if state["converged"] or state["round"] >= state["max_rounds"]:
        return "hitl"
    return [Send("agent_turn", {"agent_id": aid, **state})
            for aid in state["active_agent_ids"]]   # next debate round
```

`agent_turn_node` resolves the agent's model (§9), builds the ReAct agent, invokes it against the blackboard, and returns an additive `{"contributions": [...], "critiques": [...], "events": [...]}`.

## 8. Consensus engine (the math)

**Termination** (locked): a round ends when **either** condition holds:
- `round >= max_rounds` (default `max_rounds = 3`), **OR**
- `mean(confidence over latest-round contributions) >= τ` (default `τ = 0.85`).

**Selection** (locked): once terminating, run a **confidence-weighted vote**. Each agent's latest contribution is weighted by its (normalized) confidence; the synthesizer is handed the ranked list. Optionally, agents cast a vote for the best peer contribution, weighted the same way.

```python
def evaluate_consensus(state: CollabState) -> dict:
    latest = [c for c in state["contributions"] if c["round"] == state["round"]]
    mean_conf = sum(c["confidence"] for c in latest) / max(len(latest), 1)
    converged = mean_conf >= state["confidence_threshold"]

    # weighted ranking (normalize confidences to weights)
    total = sum(c["confidence"] for c in latest) or 1.0
    ranked = sorted(latest, key=lambda c: c["confidence"] / total, reverse=True)

    return {
        "converged": converged,
        "consensus_ranking": [f'{c["agent_id"]}:{c["round"]}' for c in ranked],
        "round": state["round"] + 1,
    }
```

**Tie-break / deadlock:** if `max_rounds` is hit without convergence, proceed to HITL with the best-ranked candidate flagged "unconverged" — the human breaks the tie. All thresholds are per-team tunable in the UI.

## 8.5 Chat & Conversational Layer

A **conversational entry surface** that sits *above* the collaboration engine. The Session Workspace (§9 of the frontend) is the *observation* layer; Chat is the *input* layer. Three modes, all reusing existing primitives — **no new engine**.

### 8.5.1 Modes
| Mode | Backend path | Consensus / HITL | Persisted |
|---|---|---|---|
| **Team chat — lightweight (default)** | the collab graph parameterized `max_rounds=1`, HITL off | single round → straight to synthesis; no debate loop | yes (conversation + run-per-turn) |
| **Team chat — Deep Collaborate (toggle)** | the full collab graph (§7) | full multi-round + consensus + (optional) HITL | yes |
| **No-team chat (single LLM)** | one `create_agent` (or bare model) + checkpointer; **no graph, no mesh, no consensus** | n/a | yes |
| **Playground** | same as team chat (lightweight default + deep toggle) | per mode | **no** — `is_playground`, excluded from session history |

Key point: **lightweight team chat is not a separate system** — it's the same `build_collab_graph` run with `max_rounds=1` and `hitl_enabled=false`, so consensus immediately proceeds to the synthesizer after one parallel round. Deep Collaborate flips those flags back to the full configuration. This keeps one execution spine.

### 8.5.2 Multi-turn & threading
A **conversation** owns a checkpointer `thread_id`. Each user turn:
- **Team chat:** spawns a **run** on that thread (run-per-turn); the synthesized output is the assistant message. Context carries across turns via the checkpointer + agents' long-term memory (§10).
- **No-team chat:** invokes the single agent directly on the thread; the message is produced without a run.

A run therefore belongs to **either** a launched Session **or** a Chat conversation (see data-model change, §13).

### 8.5.3 File upload (transient by default)
Files uploaded in a chat are **transient per-conversation context** — ingested into a conversation-scoped vector namespace (reusing the knowledge pipeline, §10.5) available only to that conversation. An explicit **"Save to team knowledge"** action promotes an attachment into `knowledge_sources` (§10.5). Default = transient; nothing silently joins the team KB.

### 8.5.4 Streaming
Chat reuses the **AG-UI** event stream (§24): no-team chat emits `text`/`reasoning`/`tool_call` events; team chat emits the full round/contribution/critique/consensus/synthesis stream, so a team turn can be **expanded into the Session Workspace** for that run.

### 8.5.5 Model selection
No-team chat and the orchestrator's framing both resolve a model via the **Model Resolution Layer** (§9) — a no-team conversation stores its chosen connection/catalog/profile; team chat uses the team's agents as configured.

## 9. Model Resolution Layer

The layer that lets anyone add any model at runtime (OpenRouter-style) and have agents use it. **Four layers**, terminating in a real LangChain chat model.

```
Agent ──► Inference Profile ──► (agent model override?) ──► Catalog Model ──► Provider Connection ──► secret
                                                                                      │
                                                                                      ▼
                            translate_params(provider, profile.params)
                                                                                      │
                                                                                      ▼
        init_chat_model(model, model_provider, base_url, api_key, **params)  ──►  create_agent(model=...)
```

### 9.1 Resolution (with locked Q1: profile default model + optional agent override)

```python
from langchain.chat_models import init_chat_model
from langchain_core.language_models.chat_models import BaseChatModel

def resolve_model(agent_cfg, *, require_tools: bool = True) -> BaseChatModel:
    profile = profiles.get(agent_cfg.profile_id)
    model_id = agent_cfg.override_model_id or profile.default_model_id   # Q1
    cat  = catalog.get(model_id)            # carries supports_tools, deployment_name, model_type
    conn = connections.get(cat.provider_connection_id)

    if require_tools and not cat.supports_tools:     # Q2 hard gate for mesh agents
        raise ModelNotToolCapable(cat.display_name)

    api_key = secrets.resolve(conn.api_key_ref)      # secrets manager / decrypt — never plaintext
    params  = translate_params(conn.provider, profile.params)   # per-provider filter/rename

    return init_chat_model(
        model=cat.model_identifier,                  # e.g. "anthropic/claude-sonnet-4-6" (OpenRouter)
        model_provider=conn.provider,                # openai | anthropic | azure_openai | ollama | openrouter | openai_compatible
        base_url=conn.base_url,                      # None for first-class providers
        api_key=api_key,
        azure_deployment=cat.deployment_name,        # only for azure_openai (per-model, not per-connection)
        **params,
    )
```

### 9.2 Parameter translation (Problem #2)

Params are **not portable**. The factory must filter/rename per provider rather than splat blindly:

| Concept | OpenAI | Anthropic | Ollama |
|---|---|---|---|
| Reasoning effort | `reasoning={"effort": "high"}` | `thinking={"type":"enabled","budget_tokens":N}` | n/a |
| Context window | (model-fixed) | (model-fixed) | `num_ctx=N` |
| Sampling | `temperature` (rejected by some reasoning models) | `temperature` | `temperature` |

`translate_params` maps the profile's normalized params to each provider's accepted kwargs and **drops** unsupported ones (e.g. omit `temperature` for models that reject it).

### 9.3 Tool-calling is the hard gate
A ReAct agent must call tools. `model_catalog.supports_tools = true` is mandatory for every **mesh agent**; the agent-config model dropdown shows only tool-capable models. The **Synthesizer** node relaxes this (`require_tools=False`) and may use a cheaper non-tool model.

### 9.4 Credentials & safety (production)
- API keys live in a **secrets manager** (or envelope-encrypted at rest); the DB stores only `api_key_ref`. Keys are **write-only** in the UI (masked thereafter), never logged, never returned to the client.
- **Validation probe on save:** a 1-token completion / `models.list` call before marking a connection `validated`. (OpenRouter passes model IDs through unchanged — a wrong ID 404s at request time, so catch it in Settings, not mid-session.)
- **SSRF guard:** arbitrary `base_url` is an SSRF vector — restrict to an allowlist / public-IP validation; run inference egress from a restricted segment.

### 9.5 Embeddings (locked Q3)
Embedding models are first-class in the catalog (`model_type = "embedding"`) on the **same Connection layer**, resolved via `init_embeddings("provider:model")`. A **Default Embedding Profile** ships out of the box; users see "Memory Enabled ✓" and only touch the embedding model under advanced settings. The same embeddings power both RAG (Knowledge, §10.5) and semantic search in the long-term Store (§10).

**Vector store = pgvector** (`langchain-postgres`, `PGVector`). This keeps Knowledge, the checkpointer, and the long-term Store all inside the one Postgres you already run; it supports metadata filtering and delete-by-id, which are exactly what runtime, multi-tenant, user-uploaded knowledge needs. **Dimension gotcha:** the embedding model's output dimension is fixed into the pgvector column at creation, so changing an embedding model later requires a re-index/migration — pin the default embedding model deliberately.

## 10. Memory architecture

Two distinct mechanisms — don't conflate them:

| Scope | Mechanism | Keyed by | Purpose |
|---|---|---|---|
| Short-term (one session) | `PostgresSaver` checkpointer | `thread_id` | Blackboard persistence, HITL pause/resume, replay |
| Long-term, per-agent | LangGraph **Store** (`PostgresStore`, pgvector-indexed) via `deepagents` memory | namespace e.g. `("team", team_id, "agent", agent_id)` | Cross-session recall ("Research Agent remembers its findings") |

Short-term is automatic once a checkpointer is attached (§7). The **agent "Memory: Enabled" toggle** controls *long-term* memory. **We use LangChain/`deepagents` shipped memory — not custom glue.** (Earlier drafts hand-wrote a recall middleware + record schema; that's replaced by the configured backend below.)

### 10.1 Long-term memory = `deepagents` memory on the Store

We already use `deepagents` for skills (§11), so we use its memory feature too — it mounts a persistent `StoreBackend` at `/memories/` through a `CompositeBackend`, while ordinary thread-scoped scratch stays in `StateBackend`. The agent reads and writes memory through the standard filesystem tools; nothing about recall or writing is hand-rolled.

```python
from langchain.agents import create_agent
from deepagents.middleware import FilesystemMiddleware
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend

agent = create_agent(
    model=resolve_model(cfg),
    store=store,                                   # PostgresStore (pgvector-indexed)
    middleware=[
        FilesystemMiddleware(backend=CompositeBackend(
            default=StateBackend(),                # ephemeral, thread-scoped
            routes={"/memories/": StoreBackend()}, # persistent, cross-session
        )),
    ],
)
```

`StoreBackend` accepts a namespace factory, so memory is isolated per `(team, agent)` — that *is* the per-agent memory. The same `PostgresStore`, pgvector-indexed, gives semantic recall.

### 10.2 What we configure (instead of code)

The behaviors the earlier draft specified by hand are configuration dimensions of the shipped memory feature:

| Dimension | Our setting |
|---|---|
| Duration | short-term (StateBackend) + long-term (StoreBackend at `/memories/`) |
| Information type | episodic (past findings), semantic (facts), procedural (overlaps with skills, §11) |
| Scope | agent-scoped by default; team-scoped namespace for shared memory |
| Update strategy | during-conversation writes; optional **background consolidation** between runs |
| Retrieval | loaded on demand via the memory filesystem tools (no custom recall middleware) |
| Permissions | read-write for the owning agent; read-only for shared team policies |

"Memory: Enabled" off → no `/memories/` route is mounted and no namespace is created.

### 10.3 Short-term context management (also shipped)

To keep long debates inside the context window, use the **built-in** middleware — `SummarizationMiddleware` and/or `trim_messages` in a `before_model` step — rather than a custom trimmer. This is the "manage short-term memory" feature, not bespoke code.

### 10.4 Shared (blackboard) vs private (memory) — the one genuinely custom piece

The **blackboard** (§6) is the *shared* round-by-round working state every peer reads — this is our domain logic (the mesh), not a memory feature, and stays custom. The **Store/memory** above is each agent's *private* long-term recall across sessions. They never mix: a critique an agent keeps privately is distinct from what it publishes to the mesh.

## 10.5 Knowledge & RAG (pgvector)

This is the layer that makes the **Knowledge** panel from the agent-config screen functional (files / URLs / databases / team docs). The original draft only had a `knowledge` JSONB column and a UI component — no pipeline. Here is the real architecture.

### 10.5.1 Ingestion pipeline (on source upload, async)

```
Source (file | URL | DB rows | team doc)
   │  loader            (PyPDF / web loader / CSV / etc.)
   ▼
Raw documents
   │  split             (RecursiveCharacterTextSplitter — chunk + overlap)
   ▼
Chunks
   │  embed             (init_embeddings — the team's embedding model)
   ▼
PGVector.add_documents(chunks, metadata={team_id, agent_id|null, source_id, scope})
```

Each chunk carries metadata so retrieval can be filtered by tenant and scope. `agent_id = null` means a **team-shared** source; a set `agent_id` means **agent-private** knowledge.

```python
from langchain_postgres import PGVector
from langchain.embeddings import init_embeddings

vector_store = PGVector(
    embeddings=init_embeddings(team.embedding_model),   # default embedding profile
    collection_name="knowledge",
    connection="postgresql+psycopg://...",
)
vector_store.add_documents(chunks)   # chunks carry metadata: team_id, agent_id, source_id, scope
```

### 10.5.2 Retrieval as a tool (what the agent actually calls)

The agent gets a `search_knowledge` tool backed by a **metadata-filtered retriever** so it only ever sees knowledge it's entitled to:

```python
from langchain_core.tools import tool

def make_knowledge_tool(vector_store, team_id, agent_id, only_specified_sources, source_ids):
    flt = {"team_id": team_id}
    if only_specified_sources:                 # the "Only use specified sources" toggle
        flt["source_id"] = {"$in": source_ids}
    # team-shared OR this agent's private knowledge
    flt["agent_id"] = {"$in": [None, agent_id]}
    retriever = vector_store.as_retriever(search_kwargs={"k": 6, "filter": flt})

    @tool
    def search_knowledge(query: str) -> str:
        """Search the team/agent knowledge base for relevant passages."""
        docs = retriever.invoke(query)
        return "\n\n".join(f"[{d.metadata['source_id']}] {d.page_content}" for d in docs)

    return search_knowledge
```

### 10.5.3 The two source-scoping toggles (from your screenshot)

- **"Only use specified sources"** → RAG is restricted to the `source_ids` the user attached (the metadata filter above). Off → search the whole team knowledge base.
- **"Search all websites"** → this is *not* RAG; it's the **web-search capability** (a separate tool). On → the agent may call live web search in addition to (or instead of) ingested knowledge. This cleanly separates "retrieve from what we ingested" (RAG) from "go look it up live" (web search) — they're different tools, both optional per agent.

### 10.5.4 Capabilities → tools mapping

The agent-config **Capabilities** toggles map to predefined tools added to the agent at spawn:

| Capability (UI) | Backing tool |
|---|---|
| RAG / Knowledge | `search_knowledge` (§10.5.2) |
| Web Search | live web-search tool (the "Search all websites" toggle) |
| Code Interpreter | sandboxed code-exec tool |
| Create documents/charts | doc/chart generation tools (Word/Excel/PPT/chart) |
| Create images | image-generation tool |

All are entries in the predefined tool registry (§11/§12); the agent's `create_agent(tools=[...])` list is assembled from its enabled capabilities + skills.

Skills follow the open **Agent Skills spec** (`agentskills.io`): a folder per skill containing `SKILL.md` with YAML frontmatter (`name`, `description`) plus instructions and optional `scripts/`, `references/`, `assets/`.

```
skills/
└── market-research/
    ├── SKILL.md          # frontmatter (name, description) + instructions
    ├── scripts/
    └── references/
```

**Progressive disclosure:** only each skill's `name` + `description` is loaded into the agent prompt at startup; the full `SKILL.md` is read **only when the task matches**. Layering (locked): filesystem **base skills** are overlaid by **UI-uploaded skills** (last-wins on name collision), so teams can add skills from the workspace without redeploying. Resolution uses the deepagents `skills=[...]` argument with a filesystem backend for base + a store-backed layer for uploads.

## 12. Middleware stack (guardrails, HITL, context engineering)

v1 middleware runs `before_agent → before_model → wrap_model_call → after_model → after_agent` (before hooks first-to-last, after hooks last-to-first). Used for:

- **HITL:** `HumanInTheLoopMiddleware(interrupt_on={...})` before the Synthesizer.
- **Guardrails:** PII redaction / content policy as `after_model` middleware; deterministic, independent of the model.
- **Context engineering:** `before_model` middleware trims/compresses the blackboard slice each agent sees (avoids O(N²) context blow-up as agents/rounds grow).
- **Dynamic model selection (future):** `wrap_model_call` to swap the model per task at runtime.

## 21. System Architecture Document (SAD)

### 21.1 Scope & stakeholders
A multi-tenant platform where users compose **Teams** of peer ReAct agents and run decentralized collaboration sessions. Stakeholders: end users (build teams, launch runs, act as the HITL approver), platform admins (manage provider connections, base skills, RBAC), and the engineering team (this spec set).

### 21.2 Architectural views
- **Logical view** — components in §4 (Orchestrator, Agent Mesh, Blackboard, Consensus, HITL, Synthesizer, End).
- **Process/runtime view** — the LangGraph control graph in §7 (outer DAG + inner `Send()` mesh).
- **Data view** — §13 (relational schema) + pgvector (knowledge & memory) + checkpointer/store.
- **Deployment view** — §21.3 (new).

### 21.3 Deployment view

        └─────┬─────┘    └─────┬─────┘      └─────┬─────┘

- **FastAPI (N replicas)** behind a load balancer; each serves REST + WebSocket.

- **PostgreSQL + pgvector** is the single system of record: app tables (§13), knowledge vectors (§10.5), LangGraph checkpointer + store (§10).
- **Ingestion worker(s)** handle knowledge uploads asynchronously.
- **Secrets manager** holds provider API keys (§9.4).
- **LangSmith** for tracing (§17 NFR-4).

### 21.4 End-to-end run sequence

```
User ──query──► POST /sessions/{id}/run
  │
  ▼
Orchestrator node      writes goal + per-agent framing to blackboard; spawns agents
  │                    ── AG-UI: run_start, round_start
  ▼
Mesh Round (Send → all agents in parallel)
  │  each agent: resolve model → assemble tools/skills/memory → ReAct loop
  │              writes Contribution(+confidence)+Critiques to blackboard
  │  ── AG-UI: agent_turn_start, reasoning, tool_call, tool_result, contribution, confidence, critique
  ▼
Consensus node         mean(confidence)≥τ OR round≥max? → converged
  │  ── AG-UI: consensus_update
  ├── not converged & round<max ──► next Mesh Round (loop)
  ▼ converged / max
HITL Gate (interrupt)  ── AG-UI: hitl_request ;  run pauses (state persisted by checkpointer)
  │
  ▼  POST /sessions/{id}/resume {approve|edit|reject}
Synthesizer node       merges consensus_ranking into final output  ── AG-UI: synthesis
  ▼
End node               persist artifact; ── AG-UI: run_finished
```

Every transition is checkpointed; a crashed or paused run resumes from the last checkpoint on the same `thread_id`.

### 21.5 Failure handling
- **Model/API error** — chat models auto-retry with backoff (§17 NFR-5); on exhaustion the `agent_turn` records a failed-contribution marker (confidence 0) so the round still completes rather than deadlocking.
- **Agent timeout/crash** — per-`agent_turn` timeout; a missing contribution is treated as abstention for that round. The mesh degrades gracefully (fewer voices), it doesn't stall.
- **Idempotency** — `agent_turn` is keyed by `(run_id, agent_id, round)`; retries must not double-append to the blackboard (§22.5).
- **Resume** — HITL pause, deploy restart, or crash → resume via checkpointer; no work is lost between checkpoints.
- **Byzantine / hallucinated output** — mitigated by design: peer **critiques** + **confidence weighting** down-weight bad contributions, and the **HITL gate** is the final backstop. Reputation/Byzantine quorum is deferred (§18).

### 21.6 Cross-cutting concerns
Security (§9.4, §26.4), observability (§17 NFR-4), config precedence (global → team), and multi-tenancy isolation (every knowledge/memory/query path is filtered by `team_id`, agent-private vs shared by `agent_id`).

## 22. Agent Runtime Specification

### 22.1 Lifecycle
```
AgentConfig (DB) ──spawn──► resolve model (§9) ──► assemble(tools+skills+memory+middleware)
   ──► register in CollabState.active_agent_ids ──► [per round] invoke ──► teardown at run end
```
Agents are spawned per run (runtime spawning); they do not persist as long-lived processes in v1.

### 22.2 The `agent_turn` node contract
**Input:** `{ agent_id, <blackboard slice> }` (from `Send`). The slice is the goal, this agent's framing, and the current `contributions`/`critiques` (optionally context-trimmed by middleware, §10.3).

**Build (per turn or cached):**
```python
agent = create_agent(
    model=resolve_model(cfg, require_tools=True),     # §9.1, tool-calling gate
    system_prompt=render_prompt(cfg, blackboard),     # persona + goal + peer state
    tools=assemble_tools(cfg),                        # capabilities (§10.5.4) + skill tools
    store=store,                                      # long-term memory (§10)
    middleware=[
        AgentMemory/FilesystemMiddleware(...),        # §10.1 (deepagents memory)
        SummarizationMiddleware(...),                 # §10.3 short-term context mgmt
        # guardrail middleware (§12) as needed
    ],
    response_format=ContributionOut,                  # structured output, §22.3
    checkpointer=checkpointer,
)
```

**Invoke:** run the ReAct loop against the blackboard slice; the agent may call tools/skills and read/write its memory.

**Output (additive to CollabState):** `{"contributions":[Contribution], "critiques":[Critique], "events":[...]}` (reducers in §6 merge parallel writes).

### 22.3 Structured output
Each turn must return a typed result so consensus can score it deterministically:
```python
from typing import TypedDict, Annotated
class ContributionOut(TypedDict):
    content: Annotated[str, ..., "this agent's proposal/answer for the round"]
    confidence: Annotated[float, ..., "0–1 self-assessed confidence"]
    critiques: Annotated[list[dict], ..., "optional critiques of peers' prior contributions"]
```
Bind via `create_agent(response_format=ContributionOut)` (ToolStrategy/ProviderStrategy, §5).

### 22.4 Tool / skill / memory assembly
- **Tools** = predefined registry entries selected by the agent's enabled **capabilities** (§10.5.4) + the **A2A intent tools** (§23.4).
- **Skills** = base (filesystem) + uploaded (store), layered last-wins (§26.3); only name+description loaded until matched.
- **Memory** = `/memories/` StoreBackend mounted iff `memory_enabled` (§10.1).

### 22.5 Concurrency, determinism, idempotency
- **Parallelism:** all active agents run concurrently per round via `Send()`; use async model clients.
- **Isolation:** an agent's tool calls and memory writes are scoped to its own namespace; only its returned `Contribution`/`Critique` reach the shared blackboard.
- **Idempotency key:** `(run_id, agent_id, round)`. The node checks for an existing contribution with that key before appending; retries overwrite, never duplicate.
- **Cancellation:** a per-turn timeout cancels a stuck agent; its slot becomes an abstention (§21.5).

## 23. Custom A2A Protocol Specification

> **Design note (consistent with §18):** v1 does **not** put agents on a network. This "A2A" is a **message contract realized over the shared blackboard** — every message is a structured record written to / read from `CollabState`. The contract is defined as a standalone protocol so that, if agents later split into separate services, the *same envelope* maps onto an HTTP/queue transport (or the open A2A standard) with no change to agent logic. Building the network transport is deferred; defining and using the envelope is not.

### 23.1 Why a contract (not free-text)
The mesh requirement ("any agent may inform, request, delegate, critique, endorse any other") needs typed intents so consensus and the UI can interpret interactions — not unstructured chatter. The contract gives that structure while keeping delivery on the blackboard.

### 23.2 Message envelope
```python
class A2AMessage(TypedDict):
    id: str
    run_id: str
    round: int
    sender: str                 # agent_id
    recipients: list[str] | Literal["*"]   # "*" = broadcast (the usual case)
    intent: Literal["INFORM","REQUEST","PROPOSE","CRITIQUE","DELEGATE","ENDORSE","VOTE"]
    in_reply_to: str | None     # correlation id for threading
    payload: dict               # intent-specific body
    confidence: float | None
    ts: str
```

### 23.3 Intents (performatives)
| Intent | Meaning | Payload |
|---|---|---|
| `INFORM` | share a finding/fact | `{content}` |
| `REQUEST` | ask a peer for info/help | `{question, target_capability?}` |
| `PROPOSE` | put forward a solution piece | `{content}` |
| `CRITIQUE` | challenge a peer's reasoning | `{target_msg_id, severity, content}` |
| `DELEGATE` | hand a subtask to a peer | `{subtask, target}` (v1: advisory; no auto-spawn) |
| `ENDORSE` | agree with a peer | `{target_msg_id}` |
| `VOTE` | weighted vote in consensus | `{target_msg_id, weight}` |

### 23.4 Realization in v1 (over the blackboard)
- Agents emit messages by appending `A2AMessage`s to a `messages` channel on `CollabState` (additive reducer, like `contributions`).
- **Broadcast** (`"*"`) = visible to all peers next round (the default mesh behavior — "everyone reads the board").
- **Directed** (`recipients=[agent_id]`) = the framing/middleware for that recipient surfaces it in its next turn.
- **Delivery semantics:** at-least-once, **eventually visible next round** (no synchronous request/response within a round; a `REQUEST` in round *n* is seen and answered in round *n+1*). This is intentional — it preserves parallelism and avoids intra-round deadlock.

### 23.5 Anti-chaos (prevents O(N²) message storms)
- **Per-agent message budget per round** (e.g. ≤ M messages); excess is dropped with a warning event.
- **Priority + dedup:** `CRITIQUE`/`VOTE` outrank `INFORM`; near-duplicate `INFORM`s are deduped by semantic similarity before being added to peers' context.
- **Context trimming** (§10.3) bounds how much of the message history each agent sees.

### 23.6 Versioning & transport-forward path
- Envelope carries an implicit `v1` schema; add a `schema_version` field before any breaking change.
- **Future transport:** when an agent becomes a service, `recipients`→ routing, `intent`/`payload` → request body, `in_reply_to` → correlation header. An "agent card" (capabilities/skills advertisement) would be published per agent — this aligns with the open A2A standard, so adopting it later is a transport swap, not a redesign. **Do not build this in v1.**

## 24. AG-UI / A2UI Specification

### 24.1 Roles (do not conflate)
- **AG-UI** = Agent↔User **interaction** protocol: streams typed execution events backend→frontend (and user actions frontend→backend). This is what powers the live collaboration view.
- **A2UI** = generative-UI spec: agents emit a declarative **component tree** the client renders with native widgets. **Deferred** (§18); the seam is designed here.

### 24.2 Transport
- Server→client: **SSE or WebSocket** at `WS /sessions/{id}/stream`. WebSocket preferred (bidirectional, supports user actions like HITL decisions inline).
- Client→server actions (HITL approve/edit/reject) may also go via `POST /sessions/{id}/resume`.

### 24.3 Event envelope
```jsonc
{ "type": "<event_type>", "session_id": "...", "run_id": "...", "seq": 1234, "ts": "...", "data": { } }
```
`seq` is a monotonic per-run sequence for ordering and replay.

### 24.4 Event catalog
| Event | When | Key data |
|---|---|---|
| `run_start` | run begins | goal, agent roster |
| `round_start` | each debate round | round number |
| `agent_turn_start` | an agent begins its turn | agent_id |
| `reasoning` | agent reasoning delta | agent_id, text |
| `tool_call` | agent calls a tool/skill | agent_id, tool, args |
| `tool_result` | tool returns | agent_id, tool, result |
| `contribution` | agent posts its round result | agent_id, content_blocks (§24.6) |
| `confidence` | agent's self-score | agent_id, value |
| `critique` | peer critique (A2A CRITIQUE) | sender, target, severity |
| `consensus_update` | after consensus node | mean_confidence, ranking, converged |
| `hitl_request` | run pauses for human | candidate output, options |
| `hitl_resolved` | human decided | decision |
| `synthesis` | synthesizer output | content_blocks |
| `run_finished` | terminal | artifact id |
| `error` | any failure | scope, message |

### 24.5 Multi-worker fan-out
A run executes on one FastAPI replica but a client may be connected to another. The executing node publishes each event to **Redis pub/sub** on channel `run:{run_id}`; every replica's WebSocket handler subscribes and forwards to its connected clients. Single-replica dev needs no Redis.

### 24.6 Content blocks (the A2UI seam)
`contribution`/`synthesis` data carry a typed `content_blocks` array; the React renderer switches on block `type`:
```jsonc
"content_blocks": [
  { "type": "text", "value": "..." },
  { "type": "tool_result", "tool": "search_knowledge", "value": "..." },
  { "type": "confidence", "value": 0.82 }
  // FUTURE (A2UI): { "type": "a2ui_component", "tree": { /* declarative widget tree */ } }
]
```

### 24.7 A2UI (deferred, designed)
When enabled, an agent may emit an `a2ui_component` block: a **declarative JSON component tree** (no executable code crosses the trust boundary). The client maps abstract nodes (card/form/button/table) to its own React components and validates the tree against an allowlisted schema before mounting. v1 ships the block type in the schema but renders only the non-A2UI block types; adding A2UI later is one render branch + a validator, no protocol change.

### 24.8 Reconnection / replay
On reconnect, the client sends the last `seq` it saw; the server replays missed events from the checkpointed event log (the `events` channel, §6) and resumes the live stream.

## 25. Memory Architecture Document

This extends §10 (which holds the primary design: `deepagents` memory over a pgvector-indexed `PostgresStore`, plus the checkpointer for short-term). Engineering details:

### 25.1 Namespace taxonomy
| Namespace | Scope | Written by |
|---|---|---|
| `("team", team_id, "agent", agent_id)` | private agent memory | the agent |
| `("team", team_id, "shared")` | team-shared policies/notes | admins / endorsed memories (read-only to agents) |

### 25.2 Information types (mapped to §10.2)
Episodic (past run findings), semantic (facts), procedural (instructions — overlaps with skills, §26). Stored as Store records; `content` is embedded for semantic recall.

### 25.3 Write & consolidation
- **During-conversation:** agents write through the memory filesystem tools (`/memories/...`).
- **Background consolidation (optional job):** between runs, a scheduled task summarizes and dedups an agent's recent memories (merge near-duplicates by cosine similarity), bounding namespace growth. Runs on the cheap `small_model`.

### 25.4 Retention, eviction, privacy
- Per-namespace size cap; on overflow evict oldest/least-salient.
- PII: do not write secrets/credentials to memory; a guardrail middleware (§12) may redact before write.
- Deletion: deleting a team/agent cascades to its memory namespace and knowledge vectors.

### 25.5 Boundary with the blackboard
Reaffirmed (§10.4): the **blackboard** is shared, ephemeral-per-run mesh state (custom domain logic); **memory** is private, cross-run recall (shipped feature). They never merge.

## 26. Skills Framework Specification

Extends §11 (`deepagents` skills, agentskills.io spec, filesystem base + UI-uploaded layered).

### 26.1 SKILL.md schema
```md
---
name: market-research            # required, unique within a source
description: Use this skill when ... (when-to-use; this is what the agent sees up front)
---

# Market Research
## Instructions
1. ...
## Resources
- references/sources.md — when to consult
- scripts/fetch.py — what it does
```
Frontmatter is required (`name`, `description`); body is markdown instructions. Optional `scripts/`, `references/`, `assets/`.

### 26.2 Loading & progressive disclosure
At agent build, each available skill's **name + description only** is injected into the system prompt. When a task matches a description, the agent reads the full `SKILL.md` (and referenced resources) on demand. This bounds prompt size regardless of how many skills exist.

### 26.3 Layering & precedence
Sources, lowest→highest precedence: **filesystem base skills** → **team UI-uploaded skills**. On a name collision the later (uploaded) wins (last-wins). Configured via the `deepagents` `skills=[...]` argument: a filesystem backend for base + a store-backed layer for uploads.

### 26.4 Security (uploaded skills)
Uploaded skills are untrusted input — treat accordingly:
- **Path safety:** reject symlinks/paths resolving outside the skill root; no `..` traversal.
- **Limits:** size caps on `SKILL.md` and assets; reject binaries outside an allowlist.
- **No secrets:** scan frontmatter/body for credential patterns; reject.
- **Script execution:** any `scripts/` run only in a sandboxed code-exec backend (never on the host); off by default.
- **Review:** optional admin approval before an uploaded skill becomes active team-wide.

### 26.5 Lifecycle
`author/upload → validate (§26.4) → index name+description → activate on match → (optional) admin approve/revoke`. Stored per §13 (`skills` table, `source` = filesystem|uploaded).

## 27. Model Provider & Resolution Specification

Extends §9 (Connection → Catalog → Profile → resolve → `init_chat_model`/`init_embeddings`; param translation; tool-calling gate; secrets/SSRF/validation).

### 27.1 Provider contract (required fields per type)
| Provider type | Required connection fields | Per-model (catalog) fields |
|---|---|---|
| `openai` | api_key_ref | model_identifier |
| `anthropic` | api_key_ref | model_identifier |
| `azure_openai` | endpoint, api_key_ref, api_version | model_identifier, **deployment_name** (per-model) |
| `ollama` | base_url (e.g. `http://host:11434`) | model_identifier |
| `openrouter` | api_key_ref | model_identifier (`org/model`) |
| `openai_compatible` | base_url, api_key_ref | model_identifier |

### 27.2 Discovery endpoints
| Provider | Discovery | Yields |
|---|---|---|
| Ollama | `GET /api/tags` | local model ids |
| OpenAI / OpenAI-compatible / OpenRouter | `GET /v1/models` (or `/api/v1/models`) | model ids |
| Others | manual registration | — |
Discovery yields **identifiers only**; capabilities (tool-calling, context, vision) are seeded from **models.dev** and may be manually overridden (§ locked Q2). `supports_tools` gates mesh-agent eligibility (§9.3).

### 27.3 Validation probe (on connection/model save)
A cheap call (1-token completion or `models.list`) before marking `validated`. Catches bad keys, wrong `base_url`, and (for pass-through providers like OpenRouter) wrong model identifiers — which otherwise 404 only at request time. Unvalidated connections/models do not appear in agent dropdowns.

### 27.4 Resolution & caching
Resolution chain per §9.1 (agent → profile → override? → catalog → connection → secret → `init_chat_model`). Cache built models by `(catalog_id, profile_id)`; invalidate on any connection/catalog/profile edit (and on key rotation). `small_model` is resolved the same way for the orchestrator/synthesizer.

### 27.5 Parameter translation
Per §9.2 — normalize profile params to each provider's accepted kwargs, drop unsupported (e.g. omit `temperature` for reasoning models that reject it). `translate_params` is unit-tested per provider (§20 note 3).

### 27.6 Embeddings
Parallel resolution via `init_embeddings("provider:model")`; embedding models are catalog entries with `model_type="embedding"` (§9.5). The default embedding profile is sticky due to the pgvector dimension constraint (§20 note 6).
